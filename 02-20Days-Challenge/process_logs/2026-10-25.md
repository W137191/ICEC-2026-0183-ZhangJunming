## App v1.2 定时修复（回应用户"你就不能每五分钟就记录一次吗，你看这表格一点都不规整"）

### 问题定位
- 用户看复测 CSV 发现时间列不规整：短视频实际采样点为 0/6/21min + 重启后 7/52min，
  高帧率游戏为 0/14/28min + 重启后 15min，与"每 5 分钟一次"的网格差得远
- 根因：`MonitorService` 旧版用 `postDelayed` 递归排下一次采样——进程一旦被系统回收，
  Handler 链随之死亡；`START_STICKY` 重启时机不定 → 7~45min 采样空档；且重建时
  无条件补采 0min 起点 → "重启 0min 残片"污染 elapsedMin 列
- 证据链：14:36 与 16:06 两次 App 重启均产生 0min 残片；16:22 一条读数被重复记录
  3 条（双路触发 + 重启补采的叠加症状）

### 修复方案（v1.2，三级保障）
1. **绝对网格调度**：`nextTick = startTimestamp + N×间隔`（墙上时钟），单次回调早晚
   不影响后续网格点，杜绝漂移累积
2. **看门狗闹钟**：每个网格点挂 `AlarmManager.setAndAllowWhileIdle(RTC_WAKEUP)`，
   进程被杀后由系统唤起 `TickReceiver` 重新拉起服务补采；用 `setAndAllowWhileIdle`
   而非 `setExactAndAllowWhileIdle`，**不需要精确闹钟权限**，免去用户授权步骤
3. **重启不盲采**：服务重建时仅当网格点真正到期才补采一条，`elapsedMin` 按墙上
   时钟如实计算；迟于网格点超 90s 在备注标注「定时延迟Xs(系统回收进程或定时被
   推迟)」；另有 30 秒去重窗口防 Handler/看门狗双路触发重复记数
- 工程细节：`onStartCommand` 加 `removeCallbacksAndMessages(null)` 保证同一时间只有
  一条调度链；wakeLock 先释放再获取防泄漏；采样与文件 IO 全部下沉 handler 线程

### 数据侧处置（不丢弃、不涂改）

## App v1.3 二次修复（回应用户"为什么还是这样，不是每五分钟记录一次"）

### 问题再定位（v1.2 仍残留 0min 残片）
- 用户用 Release 版 v1.2 复测（`battery_heat_samples(5).csv`，高帧率游戏 10-25 20:20–21:57）
  仍发现 **0min 反复出现于 20:20 / 21:04 / 21:14 / 21:28**，并伴 4 条「定时延迟」标注
- 根因比 v1.2 想的更深：`START_STICKY` 在进程被杀后会**重投递最后一次启动 intent**，
  而那条正是 `MainActivity` 点"开始监测"时发的、带 `EXTRA_SCENARIO` 的 intent。
  v1.2 用 `intent.hasExtra(EXTRA_SCENARIO)` 判定"全新会话" → 系统重启被误判为"用户
  又点了一遍开始"→ 重置起点、补采 0min、30 分钟网格永远积不满。看门狗虽补采，但每次
  重启先插一条 0min，数据仍乱（用户实测正是此症状）

### 修复方案（v1.3）
1. **弃用 `hasExtra` 判定**：`MainActivity` 仅在用户**主动点开始监测**时写持久化标记
   `KEY_FORCE_FRESH=true`（点停止清 false）；`MonitorService.onStartCommand` 以该标记
   作为全新会话**唯一**判据，且**消费后立即清除**——任何后续 `START_STICKY` 重投递
   （无论带不带 extra）都不会再触发 0min 起点
2. **续接逻辑重写**：非全新会话从「已采样本最大 elapsedMin 之后」继续；进程被杀后重启，
   已到期网格点因 `delay<=0` 被立即级联补采填满缺格，**且不重复已采过的点**；已采满
   30min 目标网格（6 个间隔）则停止排程，避免越界重采
3. **过期兜底**：`MAX_SESSION_MS=6h`，首启 `KEY_START` 默认 0 不误判过期；即便标记残留，
   会话过期也强制开新会话而非续接陈旧起点
- 工程细节：`MonitorService` 类 KDoc 写清 v1.3 设计意图；`companion` 常量 `PREFS` 改
  `internal`（供 MainActivity 引用）、新增 `KEY_FORCE_FRESH` / `MAX_SESSION_MS`；
  参数读取与 `freshStart` 解耦（优先 intent extra，回落持久化）
